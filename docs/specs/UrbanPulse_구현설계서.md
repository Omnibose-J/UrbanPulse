**설계 원칙**
1. **요청 경로에 계산이 없습니다.** 엔진이 예측과 추천을 미리 계산해 DB에 넣고, 화면은 읽기만 합니다. 엔진은 웹 서버가 아니라 정해진 시각에 도는 작업(Job)입니다.
2. **12시간 이내는 서울시 예측을 그대로 씁니다.** 그 뒤부터 7일 뒤까지는 우리 모델이 맡습니다. 당일 오후처럼 "0일 뒤"도 포함하므로 모델은 예측 거리 0~7일로 학습합니다(실험 E2).
3. **같은 규칙으로 켜고 끕니다.** 모든 약속을 통과 / 경계 / 실패로 판정해서 켬 / 참고용 / 끔으로 다룹니다(7.0). 검증하지 않은 것은 끕니다.
4. **데이터가 늦거나 모자라면 화면에 그대로 드러냅니다.** 옛 값을 새 값처럼 보여 주지 않고, 기준을 몰래 낮추지 않습니다.
5. **정답 데이터를 스스로 쌓습니다.** 수집한 원본을 GCS에 영구 보관하고, 매일 어제 예측이 얼마나 맞았는지 계산합니다.

## 1. 구성

```
[서울시 실시간 도시데이터 API] ──30분──▶ ┌──────────── Cloud Run Jobs (Python) ────────────┐
[지하철 승하차·역 좌표]  ──매월─────────▶ │ backfill   : 처음 한 번, 과거 관측·결제 적재     │
[특일 정보 API(공휴일)]  ──매주─────────▶ │ collect    : 121곳 호출 → 원본 GCS, 파싱값 DB   │
                                          │ forecast   : 7일치 시간대 예측 + 추천 계산       │
                                          │ tier_b     : B등급 역세권 평소 흐름 재계산        │
                                          │ evaluate   : 어제 예측 vs 실제, 오차 기록         │
                                          └──────────────┬──────────────────────────────────┘
                                                         ▼
                                   [Supabase Postgres]  예측·추천·최근 관측·평가 테이블
                                                         ▲ (읽기 전용, 서버에서만)
[휴대폰·PC 브라우저] ──▶ [Vercel: Next.js] ── route handler ──┘
```

### 1.1 조각별 역할

| 조각 | 역할 | 언어·런타임 | 코드 위치 |
|---|---|---|---|
| **엔진** | 적재, 수집, 예측, 추천, B등급 흐름, 평가 | Python 3.10, Docker, Cloud Run Jobs | `app/engine/` |
| **학습** | 달력 변화율 모델 학습·검증 (노트북에서 가끔 실행) | Python | `app/engine/train/` |
| **원장** | 장소, 관측 전체, 예측, 추천, 평가 | Supabase Postgres | `app/supabase/migrations/` |
| **원본 보관** | 30분 원본 스냅샷(gzip JSON, 덮어쓰기 불가) | GCS 버킷 `<project>-urbanpulse-raw` | — |
| **화면** | 모바일 웹, PC 대시보드 | Next.js(App Router) + TypeScript, Vercel | `app/web/` |
| **연구** | 지금까지의 실험 스크립트와 데이터 (서비스에서 import하지 않음) | Python | `analysis/` |

브라우저는 Supabase에 직접 붙지 않습니다. Next.js 서버의 route handler가 service role 키로 읽습니다. RLS는 anon 전면 거부 하나만 둡니다.

### 1.2 저장소·배포

- **로컬 우선.** M0~M4는 개발 노트북에서만 돕니다: 로컬 Supabase(`supabase start`), `python -m engine <job>`, `next dev`. 원본 스냅샷은 `data/raw/`(gitignore), 30분 수집은 Windows 작업 스케줄러. 클라우드는 SOW-MC에서 한 번에 올리고, 그때 아래 배포 설명이 적용됩니다.
- `UrbanPulse/`를 git 저장소로 만듭니다(GitHub 비공개, 사용자 확인 뒤). `analysis/data/`, `.env`, 원본 스냅샷은 추적하지 않습니다. 모델 파일 `models/ratio_v1/`, `models/ratio_v1b/`(수 MB, 장소 번호표 포함)는 추적합니다.
- 엔진은 이미지 하나에 작업 여섯 개를 명령 인자로 나눕니다(`python -m engine collect` 등). Artifact Registry에 올리고 Cloud Run Jobs에 배포합니다.
- 화면은 GitHub → Vercel 자동 배포, DB 마이그레이션은 `supabase db push`로 합니다.

**클라우드 이전 준비 (SOW-L1, 계정 없이 끝낸 부분)**

### 4.1 `collect` (30분마다)

3. 파싱해서 `live_obs`, `commerce_obs`에 넣고, `city_fcst`는 최신 값으로 덮어씁니다. 파서는 `analysis/scripts/collect_rtd.py`와 `collect_cmrcl.py`를 옮겨 씁니다.
   - 업종이 하나뿐인 장소는 목록이 아닌 단일 객체로 옵니다. 두 형태를 모두 처리해야 합니다.
4. **오늘 남은 시간 갱신:** 서울시 12시간 예측으로 `forecast_hourly`를 덮어씁니다(`source=seoul`). 해당 장소의 오늘 추천도 다시 계산합니다(4.4).

   - 장소 코드 점검은 `poi_code`가 있는 장소만 비교(역세권 행에는 코드가 없음)
5. 활성 111곳 중 실패가 20곳을 넘으면 `job_runs`에 실패로 남기고 종료 코드 1로 끝냅니다.

### 4.2 `forecast` (매일 05:00)
A1·A2 장소마다 오늘부터 7일 뒤까지 시간대 예측을 만듭니다. 12시간 이내 중 `source=seoul`이 이미 있는 시간은 덮어쓰지 않습니다.

- **기준값:** 최근 3주 같은 요일·시간의 실측 평균(`live_obs`). 같은 요일이 2주 미만이면 `ready=false`입니다. 7일 뒤 예측은 불변 조건 1에 따라 2~4주 전을 씁니다.
- **변화율:** 달력 변화율 모델로 계산합니다.
  - 학습한 장소(장소 번호표에 있음)는 `ratio_v1`을 씁니다.
  - 번호표에 없는 장소(실시간 111곳 중 9곳)는 `ratio_v1b`를 씁니다.
  - 입력: 장소(또는 장소 유형), 시간, 요일, 월, 공휴일 여부, 주말과 겹친 공휴일 여부, 명절 구간, 공휴일까지 남은 날·지난 날, 예측 거리(0~7일)
  - 출력: log(실제 ÷ 3주 같은 요일 평균)
- **예측 인구 = 기준값 × exp(변화율)**
  - 근거: 처음 보는 공휴일 5일, 3일 뒤 예측에서 21.6% → 17.3% (서비스정의서 부록). 다른 예측 거리는 실험 E2 전까지 검증되지 않았습니다.
- **단계:** `level_thresholds`로 인구를 단계로 바꿉니다.
  - 경계값은 최근 90일 실측 인구와 서울시 단계를 비교해서 정합니다.
  - 규칙: 경계 k마다 "단계 k 이상인데 경계 아래인 관측 수 + 단계 k 미만인데 경계 이상인 관측 수"가 가장 적은 인구값. 같으면 낮은 값. 세 경계는 단조가 되게 보정
  - 이전 규칙(그 단계가 찍힌 가장 낮은 인구)은 이상값 하나에 경계가 내려가 단계를 높게 예측했음. 9월 실측 기준 서울시 단계와의 일치 48.6% → 79.6%(실험 17)
- **영업 활동 (A1만):** `lively_profile`에서 그날 유형과 시간의 값을 가져옵니다.
  - 날짜 유형: 설·추석 연휴는 "명절", 다른 공휴일은 "공휴일", 토·일은 "주말", 나머지는 "평일"
- 모든 예측(1·3·7일 뒤, 09~23시)을 `forecast_log`에 따로 남깁니다(평가용).
- 이어서 추천(4.4)과 비슷한 장소(4.5)를 계산합니다.

### 4.3 `tier_b` (매월, 승하차 데이터가 올라온 뒤)
121곳 밖의 역 주변에 대해 평소 흐름을 만듭니다.

1. **장소 만들기:** 역 좌표에서 반경 250m 원을 그립니다. 121곳 영역과 절반 이상 겹치는 역은 뺍니다.
2. **집계구 흐름:** 집계구 생활인구(2023-01~2026-07)에서 **공휴일을 뺀 날**만 써서 면적 비율로 합치고, 요일 유형(평일/토/일) × 시간 평균을 냅니다(`analysis/scripts/eval_fill_gap_oa.py` 방식).
3. **지하철 흐름:** 최근 3개월 하루 승하차 × 월간 시간대 비율로 만듭니다(`eval_station_fill.py` 방식). 공휴일은 뺍니다.
4. **선택 규칙:** 두 흐름의 요일·시간 상관이 **0.0보다 낮으면**(서로 반대로 움직이면) 지하철 흐름을 씁니다.
   - 기준값 0.0~0.5 모두 결과가 거의 같았습니다(흐름 상관 중앙값 0.81~0.83). 미리 정한 규칙대로 8월 데이터로 고른 0.0을 씁니다(서비스정의서 10.15).
5. 공휴일을 뺀 평소 최대(상위 10%) 대비 비율 `rel`로 바꿔 `tier_b_profile`에 넣습니다.
6. **B등급 단계:** 0 = `rel` < 0.5 "평소보다 한산", 1 = 0.5~0.9 "평소 수준", 2 = 0.9 이상 "가장 붐비는 시간대"
   - 실측 단계와 62.3% 일치했습니다(95% 신뢰구간 57.5~66.8%, 카파 0.31). 통일 규칙으로 **경계 → 참고용**입니다.
   - 그래서 화면은 단계 색보다 **흐름 곡선과 "가장 붐비는 시간대" 표시**를 중심으로 합니다.
7. **날짜별 예측:** 그날 요일 유형의 `rel` 흐름을 씁니다.
   - 공휴일 보정은 `ratio_v1b`로 **켭니다**(E1 통과, 공휴일 오차 32.7% → 28.2%).
   - 기준값을 "공휴일을 뺀 같은 요일 유형 평균"으로 정해서, 이중 조정을 막습니다. `ratio_v1b`의 목표값도 같은 기준으로 학습합니다.
8. **데이터 신선도:** 집계구 부분은 2026-07에서 멈춘 데이터입니다. 승하차 부분만 매월 새로워집니다. 250m 격자 데이터를 받을 수 있으면 교체합니다(10장).
9. **첫 구현 범위(SOW-MB):** 평소 흐름과 추천만. 공휴일 보정(`ratio_v1b`)은 뒤로 미루고, 공휴일 날짜의 B 추천은 끔. 학습에 없는 A1·A2 장소도 `ratio_v1b` 전까지 준비 중. 입력은 연구에 쓴 파일 그대로(집계구 2026-05~06, 승하차 3개월)

### 4.4 추천 계산
장소 × 날짜 × 허용도 × 목적마다 계산합니다. A1 81곳 × 3목적 + A2 30곳 + B등급 역, 각각 × 8일 × 허용도 3입니다.

1. **후보 시간**
   - **A1:** 09~23시 중 "활발한 시간"만 남깁니다.
     - 활동값 정의: 해당 업종(맛집 = 음식·음료, 쇼핑 = 유통 + 패션·뷰티, 구경·산책 = 전체) 결제 건수 ÷ 그 장소의 최근 8주 주말·공휴일 09~23시 같은 업종 결제 건수 상위 10% 값
     - 기준: 구경·산책 0.5, 맛집 0.5, **쇼핑 0.6**
     - **E3 결과에 따른 설정**
       - 구경·산책, 맛집: 추천 시간에 실제로 활발했던 비율 91~92%
       - 쇼핑: 기준 0.5에서는 실패(83.4%). 기준을 0.6으로 올린 재시험(E3b)에서 사전 기준을 통과했습니다(9월 활발 88.9%).
       - 목적 × 허용도별로 켜고 끄는 것은 아래 "켜기·끄기 표"를 따릅니다.
     - **명절(설·추석 연휴):** 영업 활동 조건을 쓰지 않습니다. 평소 공휴일 기준으로 추천하면 실제로 활발했던 비율이 57~65%뿐이었습니다(E3). A1의 명절 혼잡 기준 추천도 검증하지 않았으므로, **명절에는 A1 추천을 모두 끄고** 혼잡 예측 막대와 "명절에는 문을 닫는 가게가 많을 수 있어요"만 보여 줍니다. 명절 관측이 쌓이면 명절 전용 기준을 다시 시험합니다.
     - **외국인이 많은 장소**(명동·동대문·이태원·홍대·인사동·남대문 이름이 들어간 11곳): 별도로 판정했고, 아래 표를 따릅니다. 사람 대비 결제가 적은 곳(DDP, 동대문)은 장소별 기준을 다음에 시험합니다.
   - **A2:** 09~20시. 고궁은 `open_hours`(관람 시간·휴궁일) 안에서만 고릅니다. 목적 입력은 없습니다.
   - **B:** 09~22시. 목적 입력은 없습니다.
2. **점수** (L = 예측 단계, a = 활동값. A2·B는 a = 1로 둡니다)

| 허용도 | 점수 |
|---|---|
| 최대한 한적하게 | a − 0.6·L |
| 적당히 활기찬 게 좋아요 (기본) | a − 0.5·abs(L − 1) |
| 붐벼도 괜찮아요 | a − 0.2·max(L − 2, 0) |

3. 연속된 1~2시간을 묶어 창을 만듭니다. 점수가 높은 순으로 **겹치지 않는 창을 최대 3개** 고릅니다. 한 시간으로 사람이 몰리는 것을 조금이라도 막기 위해서입니다.
   - 창 후보는 "가도 괜찮아요"(4.4-9의 `rating = 1`) 시간만. 활발하지만 허용도를 넘는 시간은 창에 들어가지 않음. 실험 15로 재판정(7.1)
   - 오늘 날짜는 지금 시각 이후의 시간만 후보. 지난 시간의 칸은 그대로 두고 창에서만 제외. 남은 후보가 없으면 `no_window = true`
   - 저장되는 창은 모두 1시간. 2시간 창의 점수는 두 시간의 평균이라 더 좋은 한 시간을 넘지 못함(연구 코드와 같은 동작). 화면이 붙어 있는 시간을 한 범위로 묶어 표시(디자인 명세서 9.1)
4. 후보 시간이 하나도 없거나, 가장 좋은 창도 허용도를 넘는 단계(한적: L ≥ 2, 적당: L = 3)면 `no_window = true`입니다. 화면은 대안을 맨 위로 올립니다.
5. **대안 날짜 (모든 등급):** 같은 장소에서 7일 중 가장 좋은 창의 점수가 선택한 날보다 높은 날을 최대 2개 넣습니다. 항상 계산합니다.
6. **대안 장소 (A1만):** 비슷한 장소(4.5) 중 같은 시간 창의 예측 단계가 1 이상 낮은 곳을 최대 3개 넣습니다. 거리 5km 안에서만 고릅니다.
7. **설명 문구:** 규칙으로 만듭니다(LLM 없음).
   - 엔진은 문장이 아니라 **문구 코드와 값**만 저장합니다. 예) `{crowd: 1, act: "food", act_level: "lively", hours: [12,13]}` (모양과 문장 규칙은 디자인 명세서 9.3)
   - 실제 문장은 화면이 언어별 번역 파일로 만듭니다.
     - 한국어: "12~13시: 사람 보통, 음식점 활발"
     - 영어: "12–1 PM: moderate crowd, restaurants busy"
   - A2·B 문구에는 영업 활동 표현을 쓰지 않습니다.
9. **시간별 판정 `hours` (디자인 명세서 7장).** 추천을 계산할 때 09~23시 15칸을 함께 만듭니다. 한 칸은 `{"h": 14, "rating": 0|1, "in_window": bool, "reason": "fit"|"closed"|"too_busy"|"outside_hours", "crowd": 0~3 또는 B는 0~2, "act": "lively"|"quiet"|null}`.
   - `rating` 0(피하세요): A1에서 예측 활동값이 목적 기준 미달이면 `closed`, 허용도를 넘는 혼잡(한적 L ≥ 2, 적당 L = 3)이면 `too_busy`, 후보 시간 밖(A2 20시 이후·휴궁 시간, B 23시)이면 `outside_hours`. 여러 이유가 겹치면 이 순서의 앞쪽 하나(`outside_hours` → `closed` → `too_busy`)
   - `rating` 1(가도 괜찮아요): 나머지, `reason = fit`
   - `in_window`: 3단계에서 고른 추천 창에 속하면 true
   - `act`: A1만 값(`a ≥ 0.5`면 lively), A2·B는 null
   - `strip_mode`: 켜기·끄기 설정 파일의 `strip` 값. E6(디자인 명세서 7.3) 전에는 모든 조합이 `windows_only`이고, 화면은 이때 추천 창과 나머지 두 가지로만 그립니다. 엔진은 `windows_only`여도 `rating`을 계산해 저장합니다(평가에 필요)
10. 점수의 계수는 초기값입니다. 사용자 인터뷰 뒤 조정하고, 조정한 내용은 이 문서에 기록합니다.
   - "최대한 한적하게"의 혼잡 약속이 가장 약합니다. 보강 규칙 3개(가중치 1.0, 단계 1 이하만, 단계 0 우선)를 E3c에서 시험했지만 모두 실패했습니다.
   - 통일 규칙에 따라 A1의 "한적"은 세 목적 모두 끕니다(아래 표). 구경의 "한적"은 참고용이었으나 실험 15에서 활발 비율 84.4%로 기준 미달.

**켜기·끄기 표 (통일 규칙 재판정, 서비스정의서 10.15·부록 실험 13)**

| 추천 (허용도) | 한적 | 적당 (기본) | 붐벼도 |
|---|---|---|---|
| A1 구경·산책 | 끔 | 켬 | 켬 |
| A1 맛집 | 끔 | 켬 | 켬 |
| A1 쇼핑 (기준 0.6) | 끔 | 참고용 | 켬 |
| A1 외국인 많은 장소 11곳, 구경 | 끔 | 참고용 | 참고용 |
| A1 외국인 많은 장소, 맛집 | 끔 | 참고용 | 참고용 |
| A1 외국인 많은 장소, 쇼핑 | 끔 | 끔 | 끔 |
| A1 명절 (모든 목적) | 끔 | 끔 | 끔 |
| A2 공원·고궁 | 켬 | 켬 | 켬 |
| B 역세권 | 켬 | 켬 | 켬 |

- 이 표는 코드가 아니라 설정 파일(`engine/config/feature_flags.yaml`)에 둡니다. `evaluate`가 매주 다시 판정한 결과로 바꿀 수 있어야 하기 때문입니다.
- 같은 파일에 조합(목적 × 허용도 × 장소 묶음)마다 `strip: two_step | windows_only`를 둡니다. 처음 값은 모두 `windows_only`이고, E6 판정에 따라 통과·경계인 조합만 `two_step`으로 바꿉니다.
- "끔"인 조합은 추천을 만들지 않고, 화면에서 해당 칩을 "준비 중"으로 보여 줍니다. "참고용"은 추천에 "참고용" 배지를 붙입니다.
- A1 명절은 추천 없이 혼잡 예측 막대만 보여 줍니다.

### 4.5 비슷한 장소 (매일, A1만)
- **장소 특징:** 최근 4주 평균으로 만듭니다.
  - 방문객 연령 비율(10대~70대), 남성 비율
  - 업종 대분류별 결제 비중
  - 장소 유형(발달상권·관광특구 등)
- 이 특징들의 코사인 유사도로 상위 10곳을 `similar_places`에 넣습니다.
- 연령·성별 비율은 backfill 파일에 없어서 **운영 시작 후 4주가 지나야 계산할 수 있습니다.** 그 전에는 업종 비중과 장소 유형만 씁니다.

### 4.6 `evaluate` (매일 06:00)
- 어제 날짜를 목표로 한 `forecast_log`의 예측을 실측(`live_obs`)과 비교합니다. 예측 거리는 1·3·7일입니다.
- 기준값(3주 평균)과 모델의 오차(WAPE)를 평소(주말 포함)/공휴일로 나눠 `eval_daily`에 넣습니다.
- **경고 규칙 (5장 관문과 같은 기준):** 최근 4주 평소 오차에서 모델이 기준값보다 0.3%p 넘게 나쁘면 `job_runs`에 경고를 남깁니다.
- **추천 품질 점검 (A1):** 어제 추천한 창에 대해 목적별로 세 가지를 기록합니다.
  - 실측 활동값(같은 업종)이 0.5 이상인 비율
  - 우연 수준(09~23시 중 실제로 활발했던 시간의 비율)
  - 혼잡 약속을 지킨 비율. "붐벼도 괜찮아요"는 정의상 항상 지키므로 빼고 계산합니다.
- **시간별 판정 점검 (A1·A2):** 어제의 `hours` 전체를 실측과 비교해 `strip_eval_daily`에 넣습니다. "가도 괜찮아요" 칸의 실제 활발(A1)·혼잡 약속, "피하세요" 칸 중 실제로 조건에 맞지 않았던 칸 수. E6와 매주 재판정이 이 표를 씁니다.

- **입력:** 추천 품질과 시간별 판정은 `recommendation_log`(3일 전에 낸 추천)를 채점. 실제 활발 기준은 모든 목적 0.5(쇼핑의 0.6은 예측 쪽 기준). 첫 채점 가능일은 기록 시작 3일 뒤
- **매주 재판정 `rejudge`:** 표만 출력하고 `data/rejudge/`에 제안 파일 저장. 설정 파일은 `--apply`를 줄 때만 변경. 조합당 28일 또는 10곳 미만이면 판정 보류. 시간별 2단계(`strip`)는 이 작업이 바꾸지 않음(E6에서 한 번 판정)

### 4.7 보존 (작업 없음)
- `live_obs`·`commerce_obs`·`forecast_log`는 지우지 않습니다(전체 보존, 2026-10-06 결정). `lively_profile`이 공휴일·명절 유형을 전체 이력 평균으로 만들고, 기준선이 1·2·3주 전 같은 요일을 쓰므로 오래된 관측도 계산에 쓰입니다.
- 지우는 작업(`archive`)은 없습니다. DB 크기만 감시합니다: 관측 테이블은 하루 약 0.9 MB씩 자라고(2026-10-05 기준 184 MB), Supabase 무료 요금제 한도 500 MB에 가까워지면 요금제를 올립니다(`docs/RUNBOOK.md` 5장).

### 4.8 불변 조건 (테스트로 고정)
1. 예측은 예측 시점 이후의 데이터를 쓰지 않습니다. 기준값은 `target − 7k일`만 쓰고, 7일 뒤 예측은 k ≥ 2입니다.
2. A1 추천 창은 "활발한 시간" 조건을 통과한 시간만 포함합니다.
3. 인구를 단계로 바꾸는 함수는 단조입니다. 인구가 늘면 단계가 줄지 않습니다.
4. GCS 원본과 `forecast_log`는 수정하지 않습니다. DB에서 지우는 것은 4.7의 보관 절차뿐입니다.
5. 데이터가 90분 넘게 들어오지 않은 장소는 `forecast_hourly.stale = true`로 표시합니다.
6. A2·B 추천과 문구에는 영업 활동 정보가 들어가지 않습니다.
7. 기능은 켜기·끄기 표(4.4)를 따릅니다. "끔"이면 추천을 만들지 않고 화면에 "준비 중"을, "참고용"이면 배지를 표시합니다. 표에 없는 조합(검증하지 않은 것)은 끔입니다.
8. `state`가 on·reference인 행의 `hours`는 정확히 15칸(09~23시 순서)이고, off인 행은 `hours`가 비어 있습니다.
9. `in_window`인 칸은 항상 `rating = 1`이고, `in_window` 칸의 집합은 `windows`의 시간과 같습니다.
10. `rating = 0` ⇔ `reason ≠ fit`. A2·B 칸의 `act`는 항상 null입니다(불변 조건 6).
11. `strip_mode`는 설정 파일의 `strip` 값과 같고, 설정에 없는 조합은 `windows_only`입니다.

### 4.9 `integrity` (수집·예측이 끝날 때마다, 수동 실행 가능)
- 저장된 행을 읽기만 하는 점검. 모든 항목이 0건이어야 하고, 하나라도 있으면 종료 코드 1
- 언제나 성립하는 점검 18개: 불변 조건 8~10, 칸의 혼잡 단계와 그 시각 예측 단계의 일치, 오늘 창이 만들어진 시각보다 앞서지 않음, 대안 날짜·장소가 꺼졌거나 창이 없는 행을 가리키지 않음, 미래 시각의 `live`, 13시간 넘는 `seoul`, 단계 경계 순서, 결제 업종 키, 2시간 넘게 `running`인 작업 등
- 예측 직후에만 성립하는 점검 6개(`--full`): 장소별 8일 × 24시간 행 수, 추천 행 수, 지난 날짜 행, 꺼진 장소의 행, 실측 활동 표시의 범위
- `forecast`는 전체, `collect`는 언제나 성립하는 점검을 끝에 실행. 걸리면 그 실행을 `warn`으로 기록하고 목록을 `detail.integrity`에 남김

### 4.10 작업 공통 규칙 (하드닝)
- 실패하면 먼저 롤백하고, 작업 기록은 별도 연결로 `fail`을 남김. 2시간 넘은 `running` 행은 다음 실행이 `abandoned`로 닫음
- `forecast`가 화면이 읽는 표(장소 상태, 단계 경계, 활동 기준, 예측, 추천, 비슷한 장소)를 한 번에 커밋. 평가용 기록 두 표는 그 뒤
- 활성 모델이 등록돼 있는데 모델 파일이 없으면 종료 코드 1(이미지에 `models/` 포함, `MODELS_DIR`)
- 수집: 원본 쓰기 실패는 그 장소만 실패 처리, 꺼지지 않은 장소의 실패 + 무자료가 20곳 초과면 `fail`, 전체 호출 6분 제한, 원본은 임시 파일로 쓴 뒤 이름을 붙여 반쯤 쓰인 파일이 남지 않게 함
- DB 연결 실패 문구에 연결 문자열을 넣지 않음

### 6.4 API (Next.js route handler, 읽기 전용)

| 요청 | 응답 |

"지금"은 장소별 가장 최근 실측 시간(`source = live`)의 `forecast_hourly` 행. `open_quiet`의 A1은 실측 활동값(`a_actual`)이 0.5 이상인 곳만. 기대값으로 고르지 않음(실험 16). 캐시 `s-maxage=300` |

| `GET /api/flags` | 오늘 추천의 상태별 개수(등급·외국인 많은 장소·목적·허용도별). `/about`의 켜진 기능 표 |
| `GET /api/places/[id]/day?date=` | 09~23시 `forecast_hourly` + 지금 관측 + 데이터 기준 시각 + stale·ready 여부 |
| `GET /api/places/[id]/recommend?date=&tolerance=&purpose=` | `recommendations` 한 행 (창, no_window, `hours`, `strip_mode`, 대안 날짜, 대안 장소). ⑤ 하루 상세 |
| `GET /api/places/[id]/week?tolerance=&purpose=` | 오늘부터 8일의 `recommendations` 행(날짜, state, windows, `hours`, `strip_mode`). ③ 이번 주 |
| `GET /api/map?date=&tolerance=&purpose=` | 그날, 그 조건의 모든 장소 행(장소 id, 좌표, 등급, state, windows, `hours`, `strip_mode`). A2·B는 `purpose=none` 행을 함께 줌. ⑦ 지도 |

- **캐시:** 정상 응답에 `s-maxage=300`을 붙입니다. 데이터가 30분마다 바뀌기 때문입니다. 오류 응답은 `no-store`
- **입력 검증:** 날짜는 오늘~7일 뒤만(지난 날짜 410, 그 밖 400), 검색어 50자 초과 400, 없는 장소 404. 검색어는 문자 그대로 일치(괄호·`%`·`*` 포함)
- **행 수 제한:** PostgREST는 응답을 1,000행에서 자름. 1,000행을 넘을 수 있는 읽기(`/api/flags`, `/api/map`)는 끝까지 나눠 읽음
- **오늘의 추천 창:** 저장된 창 중 이미 끝난 시간은 홈 API와 화면에서 내지 않음(오늘 행은 30분마다 다시 만들어져 시각이 바뀐 직후 잠깐 남기 때문)

### 6.6 공개와 보안 머리글 (2026-10-07)
- 응답 머리글: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`(next.config). `X-Powered-By` 없음. `X-Robots-Tag`는 더 이상 보내지 않음(공개).
- Content-Security-Policy는 `src/proxy.ts`가 요청마다 nonce를 만들어 붙임(Next 안내서의 방식): `script-src 'self' 'nonce-…' 'strict-dynamic'`(개발에서만 `'unsafe-eval'`), `style-src 'self' 'unsafe-inline'`(화면이 `style=`로 색을 넣음), `img-src 'self' data: blob: https://tiles.openfreemap.org`, `connect-src 'self' https://tiles.openfreemap.org`(타일·스프라이트·글리프), `worker-src 'self' blob:`(지도 워커, 푸시 워커), `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`. 데이터 경로(`/api/*`)와 정적 파일, 프리페치 요청에는 붙이지 않음(matcher). 지도 타일 출처가 바뀌면 이 두 지시문을 함께 고침.
- 공개 파일: `robots.ts`(허용 `/ko` `/en`, 차단 `/api/` `/admin`, 사이트맵 주소), `sitemap.ts`(force-dynamic; `places` 중 켜진 A1·A2의 `/p/{id}` × 두 언어 + 정적 화면), `manifest.ts`(이름, 아이콘 192·512 PNG, maskable, 테마색 `#0f1822`), `public/og.png`(1200×630), `public/icon-192.png`, `icon-512.png`, `apple-touch-icon.png`(스크립트로 로고에서 그림). 절대 주소의 기준은 `SITE_URL`(있으면) 또는 Vercel의 `VERCEL_PROJECT_PRODUCTION_URL`; 둘 다 없으면 빌드 오류.
- 오류 경계: `app/[locale]/error.tsx`(화면 단위, 메시지 키 `state.error`·`state.retry`)와 `app/global-error.tsx`(루트 레이아웃 실패, 주소의 언어로).

### 6.5 표현 규칙
- A1·A2 단계 이름은 서울시와 같게 씁니다: 여유 / 보통 / 약간 붐빔 / 붐빔. 영어는 서울시 영문 API가 쓰는 단계 이름을 그대로 씁니다(W2에서 확인).
- B등급은 3단계로 씁니다: "평소보다 한산 / 평소 수준 / 가장 붐비는 시간대". 절대 인원은 말하지 않습니다.
- 공휴일·명절이면 날짜 탭에 이름을 붙입니다(예: "추석 Chuseok"). 해외 관광객이 한국 공휴일을 몰라도 알 수 있게 하기 위해서입니다.
- 명절에 A1 영업 활동의 근거가 약하면(명절 관측 1회) "명절에는 문을 닫는 가게가 많을 수 있어요"를 함께 보여 줍니다.
- 시간 표기는 한국어 24시간제, 영어 12시간제(AM/PM)입니다.
- 인원 숫자는 A1·A2 "지금"에만 서울시가 준 범위(예: 3,000~3,500명)로 보여 줍니다.
- 데이터가 늦으면(stale) 막대를 흐리게 하고 "데이터가 늦어지고 있어요(마지막 14:30)"라고 표시합니다.

## 10. 아직 정하지 않은 것 (구현을 막지는 않음)

- **새 경계 규칙의 낮은 예측:** 23%의 시간을 실제보다 낮은 단계로 예측. 혼잡 약속은 기준 안이지만 매주 재판정에서 확인
- **A1 "한적하게" 다시 켜기:** 실험 17에서는 구경 통과, 맛집·쇼핑 경계. 같은 8~9월 데이터를 여러 번 쓴 결과라 10월 재판정으로 결정
- **로컬 스케줄의 한계:** 노트북이 잠들면 수집·예측·평가가 모두 멈춤(2026-10-02 03:00~09:30 수집 14회 유실, 05:00 예측과 06:00 평가 미실행). 작업에 깨우기 설정을 넣었지만 실제로 깨어나는지는 미확인. 계속 돌리려면 절전 해제 또는 클라우드(SOW-MC)
- **`forecast` 실행 시간:** 장소별 일괄 예측으로 1,048초 → 91초(저장 값 동일)
- **보관 기간:** 결제 관측을 90일에서 자르면 공휴일·명절 활동 기준이 비게 됨. 기준을 합계로 따로 저장할지, 결제만 더 오래 둘지 결정 필요(`docs/tracking/findings.md`)
- **평가 시작 시점:** `recommendation_log`가 2026-10-01에 시작해 첫 채점 날짜는 10-04. E6(10월 한 달) 기간이 그만큼 짧아짐
- **서울시 API 호출 한도:** 공개 수집기가 121곳을 30분마다(하루 약 5,800회) 호출하며 운영 중입니다. 우리 키의 한도는 W3에서 확인합니다.
- **Supabase 요금제:** 보관 정책(4.7)을 넣어도 무료 500MB를 넘을 수 있습니다. W3 첫 주 실측으로 정합니다.
- **B등급 역 개수:** 역 좌표 데이터(784행, 역 이름 655개)에서 121곳과 겹치는 역을 빼 봐야 정해집니다.
- **B등급 선택 규칙의 경계:** 250m 원 방식에서는 신도림이 상관 0.26으로 기준 0.2를 살짝 넘어 지하철로 바뀌지 않았고, 이태원역은 잘못 바뀌었습니다. 기준값을 바꿀지는 더 많은 역으로 보고 정합니다.
- **"최대한 한적하게" 허용도:** 혼잡 약속이 79.4%로 기준 근처이고, 보강 규칙이 모두 실패했습니다(E3c). 다음 후보는 이 허용도에서 활동 기준을 낮추고 화면에서 알리는 방식입니다.
- **추천이 잘 안 맞는 장소:** 신도림역(맛집 활발 32%), DDP(44%), 이태원 앤틱가구거리(51%). 장소별로 추천을 끌지, 기준을 따로 둘지 정해야 합니다.
- **실측 기록의 빈칸:** 분석용으로 뽑아 둔 실측 기록은 1시간짜리 빈칸이 많았습니다(백테스트에서는 메워서 씀). 운영에서는 30분마다 직접 수집하므로 이 문제가 없어야 하고, `collect`의 수집 성공률로 확인합니다.
- **B등급의 신선도:** 집계구 부분이 2026-07에서 멈춰 있습니다. 서울시 Open API로 최신 250m 격자 데이터를 받을 수 있는지 확인해야 합니다.
- **지도:** 다국어 조건 때문에 Google Maps를 기본안으로 바꿨습니다. 무료 사용량을 넘을 경우의 비용을 확인해야 합니다. 대안은 MapLibre + 다국어 지명 타일입니다.
- **해외 관광객과 데이터:** E4에서 외국인이 많은 장소의 사람 대비 결제가 적었습니다(중앙값 3.3 대 3.9, DDP 1.1, 동대문 1.9). 다만 명동은 오히려 높았습니다(8.5). 통신 기반 실시간 인구에 외국인 관광객이 얼마나 잡히는지는 여전히 불명확합니다.
- **연휴 첫날(귀성 출발일) 예측:** 지금 모델은 개선이 없었습니다(추석 첫날 25.5% → 25.7%). 전용 특징을 넣을지는 10월 공휴일 결과를 보고 정합니다.
- **명절 영업 활동:** 명절 관측이 2026 추석 한 번뿐입니다. 2027 설이 지나야 근거가 늘어납니다.
- **대림역과 대형 공원:** 추정이 틀리는 곳입니다. 대림역은 B등급이 아니라 121곳 안(A1)에 있어 실측이 있습니다. B등급에 비슷한 성격의 역이 있으면 E1에서 걸러집니다.
