# UrbanPulse — LLM project map

Read this first. It tells an agent where each kind of file lives, who owns it, and which command proves what.
The product is described in Korean in the three specs; this map and `docs/sow/` are for the implementing agent.

## What this repo is

A Seoul hotspot timing service: for a place the visitor already chose, it tells them when (later today up to 7
days ahead) the place is open-and-lively but not at its busiest. A Python engine runs as scheduled batch jobs
and writes precomputed rows to Postgres; a Next.js app only reads them. Nothing computes on the request path.

## Entry points

| What | Command (repo root) |
|---|---|
| Local database | `cd app; supabase start` (Docker). `supabase status -o env` prints the URLs and keys that go into `.env` |
| Schema tests | `cd app; supabase test db` |
| Engine job | `python -m engine <job>` (after `pip install -e .`). Reads `.env` at the repo root; `ENGINE_SKIP_DOTENV=1` disables that |
| Load places | `python -m engine load_places` (one-off). Needs `geopandas` and `pyogrio` in the interpreter; they are not in `app/engine/requirements.txt` |
| Sync holidays | `python -m engine sync_holidays` |
| Backfill | `python -m engine backfill` (one-off; reads `analysis/data/*.csv`) |
| Collect | `python -m engine collect`. Register it with `powershell -File scripts/register_collect_task.ps1` (`-Unregister` removes the task) |
| Ingest raw | `python -m engine ingest_raw [--date YYYY-MM-DD]` |
| Train ratio | `python -m engine.train.train_ratio --holidays {research\|table} --out <dir>` |
| Evaluate ratio | `python -m engine.train.evaluate_ratio --model <dir> --grid {research\|floor}` |
| Forecast | `python -m engine forecast` (also writes `recommendations`, `recommendation_log`, `similar_places`, `lively_norm`). Register it with `powershell -File scripts/register_forecast_task.ps1` |
| Engine tests, lint | `python -m pytest app/engine/tests -q`; `ruff check app/engine` |
| Engine image | `docker build -f app/engine/Dockerfile -t urbanpulse-engine .` (context filtered by `app/engine/Dockerfile.dockerignore`) |
| Web | `cd app/web; npm run dev` → `http://localhost:3000`; `/api/health` proves the DB link |
| Mockup | open `design/UrbanPulse_시안_v6.html` in a browser |
| Research reproduction | scripts under `analysis/scripts/` (do not run unless a SOW names one; some download for hours) |

## Environment variables

`SEOUL_API_KEY`, `KASI_API_KEY`, `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RAW_DIR`,
`GOOGLE_MAPS_KEY`, `ADMIN_TOKEN`. The engine reads them via `engine.settings.require(...)`, which exits 1
naming the first missing one; the web app loads the same `.env` through `next.config.ts`. In the cloud the
host injects the same names.

## Data flow (one line per hop)

Seoul citydata API (30 min) → `collect` → `live_obs`, `commerce_obs`, `city_fcst` (+ raw snapshot to `RAW_DIR`)
→ `forecast` (05:00) → `forecast_hourly`, `recommendations` (incl. per-hour `hours`, `strip_mode`), `forecast_log`
→ web route handlers (`/api/places/[id]/week`, `/recommend`, `/api/home`, `/api/map`) → screens.
`evaluate` (06:00) compares yesterday's `forecast_log` and `recommendations.hours` with `live_obs`/`commerce_obs`
→ `eval_daily`, `reco_eval_daily`, `strip_eval_daily`; the weekly re-judgement reads those and edits
`app/engine/config/feature_flags.yaml` (on / reference / off per purpose × tolerance × place group; `strip`
two_step / windows_only). `archive` (03:00) moves rows older than 90/180 days out of the database.

## Invariants the tests must keep (build contract §4.8)

1. Forecasts use only data known at issue time. 2. A1 windows contain only lively hours. 3. Level thresholds
are monotone. 4. Raw snapshots and `forecast_log` are never modified. 5. `stale` after 90 min without data.
6. A2/B never carry commerce text. 7. Feature flags decide on/reference/off; unlisted = off. 8–11. `hours`
has 15 cells on on/reference rows, is null on off rows; `in_window` cells are `rating = 1` and equal `windows`;
`rating = 0` ⇔ `reason ≠ fit`; `strip_mode` mirrors the flag file.

## Where the numbers come from

Every figure in the specs traces to `analysis/scripts/*.py` and `analysis/data/*.csv` (backtests E1–E5, E14,
re-judgement `rejudge.py`). Bars were pre-registered before each run; the implementer never tunes them.

## Milestone order (local first)

M0 local foundation (done) → M1 places, holidays, backfill, collect (local scheduler) → M2 models →
M3 recommendations, tier B → M4 screens on `next dev` → **MC cloud** (GCP, Cloud Run Jobs, Scheduler, GCS,
hosted Supabase, Vercel, map billing decision) → M5 evaluate, archive, admin. Nothing touches a cloud account
before MC.
